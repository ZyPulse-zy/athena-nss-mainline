# 下一步：让分类数据及时到达 NSS 准入入口

唯一主线仍是自动游戏分类 → NSS RT/bulk leaf → 真人 CS2 + Steam 单 WAN 闭环。NSS36 已绑定 NSS35 并完成前置检查，但真实 WAN1 测试在开启 ECM 前因新鲜度余量不足退出，恢复通过。

1. **先核验当前 NSS35 和上轮恢复。** 读取当前 deployment-latest、现网、生产队列与 ECM 全零。完整审计曾遇到来源过旧；不要把随后一次通过当作连续新鲜，也不要把旧试装 last-error 当新崩溃。
2. **新轮次优化分类发布时延。** 现有初始准入要求 CT 起点年龄小于 1 秒；单次微测量中 CT 查询 0.28 秒、标准化 0.55 秒、分类核心 0.28 秒。先针对已测到的标准化/解析路径做相同输入的前后回放。不得缩小源范围、丢失字段、放宽重复 ID/mark/zone/NAT/元组检查、延长 TTL 或跳过门槛来求通过。
3. **检查采样周期与软件维护的耦合。** worker 在同一循环内同步维护 fallback 规则及审计，可能拉长发布间隔；这目前是源码支持的待验证假设。用只读或内存实验量化，不另开 CAKE 优化支线，不先改进程架构。
4. **验证等价与恢复，再考虑部署。** 用旧/新归一化器和分类器比较有效、畸形、截断、重复、计数回退、端口/mark/NAT 变化等输入。保留已证明的地址失败撤回、预热、冷却与独立守护语义。有明确收益后才创建新 checkpoint/独立超时回滚并做最小安装；新配置必须重新绑定控制器，旧 manifest 不能复用。
5. **只读准入窗口稳定后再集中一次真人配合。** 自然同 WAN Steam bulk TCP + CS2 UDP，完整 mark/NAT/实例相等。保存每次拒绝原因，并补来源序号、查询年龄/发布延迟的轻量记录。先确认 tag 在 ECM 学习前就绪，硬件两流分别命中 bulk/RT leaf，精确撤销通过，再评价 software→NSS→software。
6. **闭环通过才扩展。** 第二 WAN、共享预算、Wi-Fi、autorate、五 WAN 以及 bridge B-shaper/ECN/HTB dump 支线继续等待。当前单对 20 Mbps 子组不等于整个 Steam 300 Mbps 以上吞吐已进入 NSS；性能比较须明确受控范围和负载一致性。

用户本轮已集中配合一次。准备未通过前，不再要求其维持或反复开启游戏/下载。不得用合成 UDP 或 ICMP 替代真实 CS2 jitter/loss/Miss；未采集就明确未取得。

每轮保留假设、源码哈希、负载、准入记录、ECM/leaf、mark/NAT/WAN、softirq/time_squeeze/吞吐、客户端指标来源和恢复结果。NSS36 冻结证明留原目录，新候选放新轮次。
